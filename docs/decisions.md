# 설계 결정 기록

결정마다 무엇을, 왜 정했는지, 무엇을 버렸는지 남긴다. 바꿀 때는 지우지 않고 새 항목으로 대체 관계를 적는다.

## D1. 파일럿은 한 업종, 구조는 범용 (2026-10-07)

**결정:** 파일럿은 화장품 업종으로 좁게 시작하되, 업종에 따라 달라지는 것은 코드가 아니라 설정·데이터에 둔다.
범용성의 기준은 "지원 업종 수"가 아니라 "업종을 바꿀 때 코드를 고치지 않아도 되는가"다.

| 업종마다 다른 것 | 두는 곳 |
|---|---|
| 지표 적용 여부 (예: 재고회전율) | 규칙파일 `metrics_v1.yaml`의 업종별 적용 조건 |
| 시장 통계 위치 (질문 ①) | 업종 코드 → KOSIS 통계표 매핑 (데이터) |
| 비교군 | 기업 목록 + 선정·제외 사유 (데이터, 버전 관리) |
| 계정 이름 | DART 표준 `account_id` 기준 |
| 업종 판단 | 기업개황의 표준산업분류(KSIC) 코드 |

**이유:** README 5절은 V1에서 전 산업 *동시* 지원만 제외한다. 처음부터 화장품을 코드에 박으면 확장 때 다시 짜야 한다.
**버린 안:** 여러 업종을 섞은 파일럿 — 오류가 데이터·코드·업종 차이 중 어디서 왔는지 가리기 어렵다.

## D3. 자료 처리 원칙 (파일럿 검토에서 나온 것, 2026-10-07)

1. **적자·음수 영업현금흐름은 관측값이다.** 자료 부족이 아니므로 점수와 위험 신호에 그대로 반영하고, 그것만으로 부분 평가·보류하지 않는다. 부분 평가·보류는 필요한 자료가 *없을* 때만.
2. **분모 예외는 분모에서만 생긴다.** 이자보상배율의 영업이익, OCF/자산의 OCF는 분자라 음수여도 계산된다. 분모(이자비용·자산·매출·재고 등)가 0·음수인 경우는 파일럿 실제 데이터에 기대지 않고 **별도 테스트 데이터**로 준비한다.
3. **과거 시점 분석에는 당시 원본과 정정 이력이 필요하다.** 재무 API(`fnlttSinglAcntAll`)는 정정 후 최신 값을 준다. 접수번호·접수일 저장만으로는 "기준일에 알 수 있던 숫자"를 복원할 수 없으므로, 최초 보고서 원본과 정정 이력(정정 전·후, 접수일)을 함께 보관해야 한다. 수집 방법은 1-2 원본 저장 형태에서 정한다.
4. **보고서마다 금액 단위가 다르다.** 같은 업종 2025 보고서에서도 원·천원·백만원이 섞여 있다 (API는 원 단위). 값마다 단위를 기록하고 정제 단계에서 통일한다.

## D4. 원본 저장 형태 (2026-10-07)

**결정:** 파일럿의 원문은 접수번호별로, 재무 API 응답은 조회 조건·수집시각별로 변경 없이 보관한다. 정제된 수치는 별도로 생성하고 출처와 변환 이력을 연결한다. V1은 최신 자료 분석을 구현하며, 과거 시점 분석을 위한 원본과 정정 이력도 함께 확보한다.

**이유:** 원문의 식별 기준은 "어떤 접수번호의 문서인가", API 응답의 식별 기준은 "어떤 조건으로 언제 조회했는가"다. 원문 API는 접수번호로, 전체 재무제표 API는 기업·사업연도·보고서 코드·연결/별도로 조회한다.

**보관 범위 (V1)**

| 대상 | 규칙 |
|---|---|
| 기업 | 파일럿 5개사 (D2) |
| 사업연도 | 2022~2025 |
| 보고서 | 각 연도의 최초 사업보고서 + 수집일까지 확인된 **모든** 정정본 (중간 정정본 포함 — 최초·최신만 두면 중간 정정 이후의 기준일을 재현할 수 없다) |
| 재무 API | 연결·별도를 각각 조회해 응답 보관. "자료 없음" 응답도 기록 |
| 제외 | 분기·반기보고서 |

보고대상연도와 접수연도는 구분한다 (예: 2024 사업보고서를 2026년에 정정).

**폴더 구조**

| 경로 | 내용 |
|---|---|
| `data/raw/dart/{corp_code}/filings/{rcept_no}/original.zip` | 다운로드한 원문 그대로 |
| 같은 폴더 `metadata.json` | 보고서명·대상연도·접수일·수집일·출처·파일 해시 |
| `data/raw/dart/{corp_code}/api/fnlttSinglAcntAll/{bsns_year}/{reprt_code}/{fs_div}/{run_id}/response.json` | 조회 당시 재무 API 응답 그대로 |
| 같은 폴더 `metadata.json` | 인증키를 제외한 요청 조건·수집시각·응답 상태·파일 해시·응답에 등장한 접수번호, 원문 연결 상태 |
| `data/interim/` | 압축 해제·파싱·단위 변환 등 다시 만들 수 있는 중간 결과 |

API 응답은 보고서 폴더에 넣지 않고 응답의 `rcept_no`로 원문과 연결한다. 접수번호가 확인되지 않거나 원문과 대조하지 못했으면 그 상태도 기록한다.

**저장 규칙**
- 원본은 수정하거나 덮어쓰지 않는다. 재조회 결과는 새 `run_id`로 저장한다.
- 공개일과 수집일을 구분한다. 오늘 받은 자료를 과거에 이미 알던 자료로 취급하지 않는다.
- 원본의 숫자·단위를 그대로 보존한다. 원 단위 변환은 정제 단계에서 하고, 원래 단위와 변환 배수도 남긴다.
- ZIP이 실제로 열리는지 확인한다. 오류 응답을 ZIP으로 저장하고 성공으로 처리하지 않는다.
- 인증키는 경로·메타데이터·로그에 남기지 않는다.
- 과거 원문을 확보했다고 과거 분석이 완성된 것은 아니다. 기준일에 맞는 버전 선택·수치 추출·대조까지 통과해야 한다.

**단위:** 이번 표본의 API 값은 원 단위로 대조했다 (D2). 범용 시스템에서는 응답마다 통화·단위를 확인하도록 설계한다 (단위를 가정하지 않는다).

**첫 수집 결과 (2026-10-07, `python -m src.collectors.collect_pilot`)**

- 재무 API 응답 40건 (5개사 × 4년 × 연결/별도). 한국화장품제조 연결 4건은 `013 조회된 데이타가 없습니다`로 기록

- 인증키 노출 점검: 경로·파일 내용 모두 0건

## D5. 정제 데이터의 행 단위와 값 선택 (2026-10-07)

**결정:** 관측한 값을 보관하는 테이블(A)과 분석에 쓸 값을 고르는 단계를 분리한다.
- **A. 관측값 테이블 (정식 정제 테이블):** 출처별 값 하나 = 한 행. 같은 기간·계정이라도 출처가 다르면 별도 행으로 남긴다.
- **B. 분석용 표 (파생):** 값 선택 규칙을 적용한 뒤 A에서 만든다. `data/interim/`에 두고 언제든 다시 만들 수 있다.

**A의 한 행에 보존할 정보**

| 구분 | 필드 |
|---|---|
| 기업·재무 기준 | `corp_code`, `fs_div`(연결/별도), `sj_div`(재무제표 구분) |
| 계정 | `account_id`, 원래 계정명, 세부 구분(`account_detail`) — **`account_id`만으로 합치거나 중복 제거하지 않는다** (같은 코드가 여러 재무제표·세부 항목에 나온다) |
| 값·기간 | 원래 금액 문자열, 변환한 값, 통화·단위, `period_type`, `period_start`, `period_end` |
| 출처 | `rcept_no`, 공개일, API 응답 스냅샷 ID, 원본 행 위치, `source_column`(당기/전기/전전기) |
| 처리 상태 | 값 상태, 기간 상태, 원문 연결 상태 |

- 물리적 행 식별: **스냅샷 ID + 원본 행 위치 + 금액 열**
- **기간:** `period_type = instant`(자산·부채: `period_start` 없음, `period_end` = 해당 날짜) / `duration`(매출·현금흐름: 실제 시작일·종료일). 보고서의 사업연도와 값이 나타내는 기간은 별개다 — 2025 보고서의 전기 값은 2024 기간에 연결한다. 기간은 응답이 가리키는 접수번호의 원문에 적힌 회계기간("제 N 기 YYYY.MM.DD 부터 … 까지")으로 정하고, 확인하지 못하면 추정하지 않고 "확인 필요"로 둔다.
- **값 상태:** 숫자 0은 정상 관측값이다. 원문 값 없음(빈 값·`-`)과 숫자 변환 실패를 서로 다른 상태로 남긴다. 계정 자체가 없는 경우는 별도 커버리지 점검에서 확인한다.

**값 선택 규칙 (B를 만들 때)**
- 기본: **분석 기준일 이전에 공개된 해당 사업연도 보고서 중 최신 유효 정정본을 고르고, 그 보고서의 당기 값을 쓴다.** (`[첨부정정]`처럼 재무제표 본문을 바꾸지 않는 정정은 유효 정정본 후보에서 제외)
- 현재 API 값이 고른 보고서 버전과 연결되는지 확인한다. 과거 기준일에 맞는 값이 없으면 최신 API 값으로 대체하지 않고 **보류**한다.
- 서로 다른 보고서의 같은 기간 값이 다르면 먼저 **"동일 기간 값 불일치"**로 표시한다. 단위·기간·연결 기준·계정 범위를 확인하기 전에는 재작성으로 확정하지 않는다. 재작성으로 확인되면 성장률 등 기간 비교 지표의 비교 가능성을 따로 검토한다.

## D6. 계정 매핑 — 지표에 필요한 계정부터 (2026-10-07)

**결정:** 원본 계정과 내부 계산용 계정(`canonical_account`)을 연결한다. 규칙은 `configs/account_map_v1.yaml`, 코드는 `src/normalization/account_map.py`.
표준코드 없는 1,428개(원본 항목 수 기준, 관측값 행으로는 그 3배)를 전부 분류하지 않고, V1 지표에 필요한 13개 계정만 매핑한다.

| 상황 | 처리 |
|---|---|
| 표준코드가 있고 필요한 계정과 의미가 일치 | 재무제표(`sj_div`)·세부 구분까지 맞을 때만 매핑 |
| 표준코드가 없지만 원문으로 의미 확인 가능 | 근거(why)를 적은 **완전 일치 이름 규칙**으로 매핑 |
| 이름만 비슷하거나 후보가 여럿 | 확인 필요. 자동 선택하지 않음 |
| V1 지표에 필요하지 않음 | 원본 보존, 매핑 미룸 (SCE 포함) |

- 원본 `account_id`가 `-표준계정코드 미사용-`(또는 빈 값)이면 그대로 두고 `canonical_account`만 붙인다. 없는 DART 표준코드를 만들지 않는다.
- **대체 금지:** 금융원가·금융비용 전체를 이자비용으로, 유동부채 전체를 단기 이자부채로 쓰지 않는다. 현금흐름표의 당기순이익·현금 행은 손익·재무상태표 계정으로 쓰지 않는다.
- **이자비용:** 손익계산서 본문에 이자비용 행이 없다. 현금흐름표 조정항목의 이자비용은 후보로만 보여주고, 주석과 대조하기 전에는 쓰지 않는다.
- **단기 이자부채 = 이름·코드가 유동임을 명시하는 차입 항목의 합.** 단기금융부채·기타유동금융부채·상환전환우선주부채나 유동 구분이 없는 "차입금"·"사채"가 있으면 합계를 내지 않고 확인 필요. 구성 항목이 하나도 없으면 0으로 확정하지 않고 확인 필요. 유동 리스부채는 **포함 여부 미정**으로 합계에서 빼고 따로 표시한다.
- 상태: 매핑 성공 / 원문 확인 필요 / 자료 없음(API 013) / 값 없음(원문 빈 값) / 보류(기준일 버전 없음)

**점검 보완 (같은 날)**
- 동일 기간 값 불일치 비교 키에 **통화**를 추가했다. 표준코드 없이 계정명으로 묶인 그룹은 `nonstandard_key`로 표시해 신뢰도를 구분한다. 부호가 달라도 절댓값으로 통일하지 않는다.

**첫 점검표 (기준일 2026-10-07, `python -m src.normalization.build_account_check`)**
- 11개 계정(매출·매출원가·영업이익·당기순이익·영업CF·총자산·총부채·유동자산·유동부채·현금·재고)은 자료가 있는 모든 기업·연도·연결/별도에서 매핑 성공

- **이자비용:** 전부 확인 필요 (36건). 코스맥스·한국콜마는 현금흐름표 조정항목 후보가 있고, 나머지는 주석에서 찾아야 한다

### 2. 단기 이자부채에 유동 리스부채 포함
**단기 이자부채 = 단기차입금 + 유동성 장기차입금·사채 + 유동 리스부채 + 그 밖에 확인된 유동성 이자부채(수기 확인표)**
- IFRS 16은 리스부채의 이자비용을 인식하므로 금융 부담 비교에 포함하는 것이 일관적이다. 다만 포함 여부는 이 프로젝트 지표의 설계 결정이다 (IFRS가 이 비율의 산식을 정하지는 않는다)
- 합산 항목은 겹치지 않아야 한다: 합계 항목과 그 구성 항목이 함께 있으면 확인 필요 (`overlaps`). 리스는 재무상태표의 유동 장부금액 (미래 지급액 총액이 아님)
- 보고서에 "리스 포함"을 표시한다. 이자보상배율의 이자비용도 **리스 이자 포함** 기준으로 맞춘다

### 3. 이자비용 규칙 추가
- 현금흐름표 조정항목의 이자비용은 후보로 유지하고 주석과 대조한다
- **이자지급액(현금 기준)을 발생주의 이자비용으로 대체하지 않는다** (대체 금지 목록에 추가)
- 첫 대조 사례: 코스맥스 2025 연결 주석 29 '이자비용(금융원가)' 46,717,900,009 = 현금흐름표 조정항목 (원 단위 일치). 별도 주석 28도 17,332,415,349로 일치. 리스 이자의 별도 구분은 주석에 없음

### 4. 주석은 수기 확인표부터 → `data/manual/note_confirmations.csv`
- 기업 5개 규모에서는 자동 주석 파서보다 정확한 검증 사례를 먼저 만든다
- 저장: 기업·연결/별도·내부 계정·기간·값(보고서 단위 그대로)·단위·배수·접수번호·주석/표 위치·구성 설명·확인 상태·`extraction_method = manual`·확인자·확인일
- 사용 조건: `confirmed`이고 원문 위치가 있으며, 접수번호가 값 선택 규칙(D5)으로 고른 보고서와 같을 때만. API 매핑값과 다르면 확인 필요

### 5. 기간 규칙 수정 (D5·D6의 "1년 초과 버림"을 대체)
- 잘못 붙은 날짜는 **길이가 아니라 구조로** 막는다: 원문을 평문으로 펼 때 표 셀 경계를 남기고, 기간 매치가 셀 경계를 넘지 못하게 한다
- **역순 날짜만 오류로 버린다.** 53주를 넘는 긴 기간은 날짜를 보존하고 `review_needed:unusual_length`로 표시한다 (IAS 1은 결산기 변경에 따른 1년 초과·미만 기간과 52주 보고기간을 다룬다)
- `period_is_annual`은 보고서 성격(사업보고서 11011)과 실제 회계기간(12개월 또는 52·53주)을 함께 본다. 짧은 기간도 받아들이되 연간이 아님으로 표시
- 결과: 파일럿 BS·CIS·CF 13,266행은 여전히 모두 원문 기간으로 연결되고, 긴 기간은 0건

## D8. 재무상태표 구간 확인, 매각예정항목 조정, 비교 키 수정 (2026-10-07)

### 1. 구간은 산술로 확인한다 (`src/normalization/bs_sections.py`)
- 행 순서(ord)에서 소계 행 뒤의 항목들을 구간 후보로 보고, **항목 합이 소계와 원 단위까지 같을 때만** 그 구간으로 확인한다. 순서만으로는 판단하지 않는다
- 파일럿 결과: 유동부채 108/108, 비유동부채 108/108, 유동자산 108/108(4건은 매각예정 포함) 확인. 비유동자산은 일부 회사에서 자본 항목이 자본총계 행보다 먼저 나와 구간 끝을 못 잡음 → 미확인으로 두고 쓰지 않는다
- 관측값에 `bs_section`, `bs_section_confirmed` 열 추가

### 2. 유동·비유동 의미가 확정되지 않는 계정은 자동 확정하지 않는다
- 표준코드가 있어도 유동·비유동 양쪽에 쓰이는 코드(`BondsIssued`, `Borrowings`, `LeaseLiabilities`, 파생·충당·금융부채 일반 등)와 구분 표시가 없는 비표준 이름은 **확인된 구간을 비교 키에 붙인다** (`…@current_liabilities`)
- 구간을 확인하지 못하면 자동 비교·합산에서 뺀다 (재실행 결과 67행 제외). 단기 이자부채에서도 확인된 유동부채 구간 안의 사채·차입금·리스부채만 구성 항목으로 쓰고, 미확인이면 확인 필요 후보
- 재실행: 불일치 123 → 121그룹. **M08·M09 재발 없음** — 한국콜마 유동·비유동 사채가 두 보고서에서 구간별로 같다. M09의 "잔여 차이 4.6억"은 유동 사채(2,499.0억)와 비유동 사채(2,494.4억)의 차이였음 (오매칭이 만든 가짜 차이). 대조표에 `key_fix`, `rerun_result`, `residual`로 따로 기록
- 원문을 직접 확인한 사례와 API 행만 대조한 사례는 대조표 `evidence_status`에서 계속 구분한다

### 3. 매각예정항목: 보고값과 조정값을 따로 보존한다
IFRS 5는 매각예정자산·처분집단의 자산·부채를 별도로 표시하게 하므로, **별도 행으로 표시됐다는 사실만으로 소계 포함 여부를 판단하지 않는다.**

| 값 | 정의 |
|---|---|
| `reported_value` (유동자산·유동부채 보고) | 보고서에 표시된 소계 그대로 |
| `held_for_sale` | 별도 확인한 매각예정자산(부채) |
| `held_for_sale_included` | 포함 / 미포함 / 확인 필요 / 해당 없음 |
| 조정값 (`adjusted_current_assets`·`adjusted_current_liabilities`) | 미포함이 확인된 경우에만 매각예정을 더한 값. 포함·해당 없음이면 보고값과 같다 |

- **포함:** 매각예정 행이 유동 구간 안에 있고, 그 행을 더해야 소계와 같다
- **미포함:** 유동 구간 합이 매각예정 없이 소계와 같고, 유동 + 비유동 + 매각예정 = 총계 항등식도 성립한다 (두 근거)
- 매각예정 잔액이 음수면 조정하지 않고 확인 필요 (코스맥스 2025 연결: 원문 재무상태표에 (35,423,774)로 표시, 주석은 "매각예정자산으로 분류된 자산은 없습니다", 같은 금액의 매각예정자산손상차손)
- 부채도 같은 규칙으로 따로 본다 (처분집단 부채가 있으면 분모 범위도 함께 조정). 파일럿에는 매각예정부채가 없다
- 조정 비율은 **"매각예정항목 포함 유동비율"**로 표시하고, 보고값 기준 유동비율도 함께 조회할 수 있게 한다
- 파일럿 결과: 코스맥스 연결 2022 **포함**(M03: 722,703,796,018 + 14,448,921,198 = 737,152,717,216 — 2022 보고서는 소계 안, 2024 보고서는 소계 밖), 코스맥스 연결 2024 **미포함** → 조정 942,502,901,070, 한국콜마 연결 2024 포함, 코스맥스 연결 2025 확인 필요(음수)

### 4. 이자비용 수기 확인: 금액 확인과 리스 포함 확인을 분리
- 수기 확인표에 `amount_check`(금액 대조), `scope_check`(리스 이자 포함 범위), `scope_note`, `method`(실제로 한 방법)를 둔다
- 주석과 현금흐름표 후보가 일치한 것은 **금액** 확인의 근거일 뿐, 리스 이자 포함의 근거는 아니다
- 범위가 미확인이면 상태 `candidate`(계산용 후보값 제공, 리스 포함 이자보상배율의 정상 점수 반영은 보류)
- C001·C002: 금액 확인 / 리스 이자 포함 미확인 / 방법 "원문 XML 텍스트 검색 + API 조정항목과 원 단위 비교 (화면 열람 아님)" / 확인자 claude

`candidate`(후보값, 점수 보류), `not_applicable`(해당 없음 — 매각예정 행이 없는 것은 정상)

## D10. 보류된 2025 재무지표의 주석 보완 (2026-10-07)

### 원칙
1. **이자비용과 리스 이자의 중복 합산 금지:** 리스 이자를 찾았다고 이자비용에 바로 더하지 않는다. 합계에 이미 포함됐는지(또는 별도 행인지) 확인되지 않으면 참고값·점수 보류
2. **단기 이자부채는 구성과 완전성을 확인:** 유동부채 구간의 모든 행을 이자부채 여부로 분류하고, 주석으로 구성을 확인한다. 일부 금액만 찾았으면 정상 합계로 쓰지 않는다(`component_check = 부분` → 후보값). 금융부채 전체를 이자부채로 대체하지 않는다
3. **음수 매각예정자산은 0으로 바꾸지 않는다:** 매핑 오류·표시 문제·실제 금액 중 무엇인지 먼저 보고, 주석의 "없음"이 같은 기준일·연결 범위인지 대조한다. 해소되지 않으면 조정 유동비율 보류, 보고값 유동비율은 조회용
4. **확인 결과와 방법을 분리 기록:** `amount_check`(금액), `scope_check`(리스 포함 범위), `component_check`(구성요소), `method`(실제 수행한 방법). 미확인을 확인으로 승격하지 않는다
